# The ledger stays the record; no Inngest yet

Inngest offers durable functions: steps that are remembered across crashes, `step.sleep`, `step.waitForEvent`, retries, concurrency limits and cancellation. It looks like a fit for parking and resuming runs. We don't use it. Inngest records how its functions executed, and in it a run's state lives implicitly in how far the function has got. The ledger records what the kitchen decided and what happened to each job, as explicit events replayed through a pure `transition` (ADR 0008). That record is the trust ktchn was started for, and it has to stay in ktchn's own shape and keep for as long as ktchn needs it. Running both would leave two sources of truth after a crash. The only safe rule then is that the ledger wins and Inngest just carries out an effect and reports its result. That would make Inngest a runner for the shell's effects: the queue, retries, reminder timers and waiting for answers. Those are small to build on SQLite, and Inngest would add a server process and a runtime model to learn, against the aim of ADR 0001.

Revisit if the shell starts rebuilding retries, timers and concurrency badly. Even then, Inngest would only carry out effects. It would not replace the ledger.
